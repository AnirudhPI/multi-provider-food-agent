# ADR 0004: React SPA and server-sent agent progress

- **Status:** Accepted for M4
- **Date:** 2026-11-20

## Context

M3 exposes a synchronous agent-turn endpoint and returns an accumulated operational trace. M4 needs a standalone browser interface that can collect natural-language requests, obtain a user-approved location, show progress while the local model and Swiggy search run, and render normalized restaurant data. The UI must remain a replaceable delivery layer and must not receive provider credentials or hidden model reasoning.

The product does not currently need server-side rendering, search-engine indexing, route-level backend logic, or React server components. Spring Boot already owns the backend and security boundary.

## Decision

Build the frontend as a Vite-powered React and TypeScript single-page application under `frontend/`, using npm and a committed lockfile. Do not introduce Next.js for M4 because its server runtime would duplicate responsibilities already owned by Spring Boot without satisfying a current requirement.

Use a same-origin browser API contract. The Vite development server proxies `/api` to Spring Boot on port 8080; deployed environments should use the same origin or a reverse proxy. `VITE_API_BASE_URL` remains available for an explicitly configured alternative origin.

Add `POST /api/v1/agent/turns/stream` alongside the existing synchronous endpoint. It uses server-sent events over a streaming POST response:

- `trace` events contain the existing safe `AgentTraceEvent` projection;
- one `result` event contains the final `AgentTurnResponse`;
- one `error` event contains a stable error code and safe message when execution fails.

The orchestrator accepts a trace listener but retains its original synchronous method. Progress publication therefore does not change agent policy or create a second orchestration path.

The browser requests geolocation only after a user action. Coordinates are held in React memory for the current page, sent only to the backend as turn context, never displayed, persisted, or generated by the model. The UI does not handle or store Swiggy OAuth tokens.

Use Vitest and React Testing Library for component behavior and Playwright with a mocked streaming boundary for the critical browser flow. Existing Spring integration tests verify the real streaming controller contract against deterministic model and provider fakes.

## Consequences

- The UI stays small, fast to start, and independent of a Node server at runtime.
- Users receive real model/tool progress rather than a simulated loading sequence.
- The synchronous agent endpoint remains available for scripts and compatibility.
- Browser code is typed against a project-owned contract and never imports Java, Spring AI, MCP, or provider payload types.
- Conversation history and coordinates disappear on refresh because durable session state belongs to M8.
- Playwright tests remain deterministic and do not contact Ollama or Swiggy. A separate 2026-11-20 manual smoke test verified the complete browser-to-provider path with temporary in-memory OAuth credentials and user-approved browser geolocation; it rendered five live Swiggy restaurant cards and retained no credentials or coordinates.
- A separate-origin deployment would require an explicit CORS/security decision; the initial local setup avoids that complexity through the Vite proxy.
